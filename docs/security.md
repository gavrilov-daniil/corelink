# Безопасность: гварды, секреты, незакрытые пункты

Документ описывает фактическое состояние. Всё, что спроектировано, но не написано, собрано в последнем разделе — по нему нельзя строить планы эксплуатации.

## Разделы API и кто их закрывает

| Префикс | Гвард | Заголовок | Кто ходит |
|---|---|---|---|
| `/auto/*`, `/api/sub/*` | нет | — | клиенты Happ (публично, `subscription.md`) |
| `/webhooks/:provider` | нет | подпись в теле/заголовках | платёжные провайдеры |
| `/healthz`, `/v1/*` | нет | — | health-чек, публичные справочники (тарифы, спеки провайдеров) |
| `/api/admin/*` | `AdminGuard` + проверка роли (маршрут с `@PublicRoute` — без сессии: вход и конфиг кнопки Telegram) | `x-admin-token`: токен сессии оператора либо переходный общий `ADMIN_TOKEN` | админка |
| `/internal/*` | `ServiceTokenGuard` | `x-service-token` | бот, внутренние вызовы |
| `/internal/agent/nodes/:id/*` | **исключён из `ServiceTokenGuard`**, per-node проверка в контроллере | `x-agent-token` | node-agent |
| `/internal/agent/enroll` | нет гварда: аутентифицирует сам одноразовый bootstrap-токен в теле | — | node-agent при первом запуске |

Гварды зарегистрированы глобально (`APP_GUARD`) и сами решают, относится ли к ним путь.

Третий глобальный гвард — `RateLimitGuard` — токены не проверяет, но стоит **первым** в цепочке: `AdminGuard` и `ServiceTokenGuard` отвечают на неверный токен 401, и лимитер, стоящий после них, не увидел бы ни одной попытки перебора. Порядок задан порядком объявления в `app.module.ts` и является несущим.

### Fail-closed

Пустой токен **не отключает проверку** — он закрывает раздел целиком (401 на всё). Раньше было наоборот, и пустая переменная из `.env.example` делала `/internal/*` публичным.

`core` предупреждает об этом при старте — иначе «админка не открывается» дебажили бы по 401 в браузере. Про `ADMIN_TOKEN` предупреждение в обе стороны: не задан — вход только учёткой (целевой режим, но первую учётку завести уже нечем); задан — он даёт `superadmin` в обход ролей. Про `SERVICE_TOKEN` — как раньше: пустой закрывает `/internal/*` целиком.

То же у агента: без токена (ни per-node в `node_identity`, ни общего `AGENT_TOKEN`) любой его запрос получает 401.

### Мелочи, которые ломают гварды, если о них не знать

- Путь нормализуется к нижнему регистру и без query: Express матчит роуты **без учёта регистра**, поэтому гвард, сравнивающий префикс как есть, обходился бы запросом на `/API/ADMIN/...`.
- Префикс считается совпавшим и для самого пути без слеша (`/api/admin`), и для вложенных.
- Сравнение токенов — `safeCompare` (constant-time, с предварительной сверкой длины: `timingSafeEqual` бросает на разной длине).
- `/internal/agent/*` вынесен из общего сервисного токена намеренно: агент живёт на чужой машине, и общий секрет, дающий доступ ко всему `/internal/*`, ему не выдаётся.
- `nodeId` из пути проверяется на формат uuid до запроса в БД: иначе мусор в пути давал бы 500 (`invalid input syntax for uuid`) вместо 401.

### Бот

Вебхук Telegram (`POST /tg`) закрыт заголовком `x-telegram-bot-api-secret-token`, сверяется constant-time до разбора тела. Бот **не стартует**, если `BOT_WEBHOOK_URL` задан, а `BOT_WEBHOOK_SECRET` пуст: открытый `POST /tg` означает, что кто угодно подделает апдейт от чужого `tgId`. Служебные ручки бота (`/bot/*`) закрыты тем же `SERVICE_TOKEN`.

## Секреты

| Секрет | Где живёт | Что будет при утечке |
|---|---|---|
| `SECRETS_MASTER_KEY` | env/vault | расшифровываются все креды мерчантов из дампа БД |
| `ADMIN_TOKEN` (переходный, общий) | env core; в `localStorage` админки, если оператор ввёл именно его | полный доступ к админскому API: гвард считает его `superadmin` |
| токен сессии оператора | БД только `sha256` + `localStorage` админки | доступ в объёме роли этой учётки — до истечения (7 суток) или отзыва сессии |
| `client_secret` входа по Telegram | БД (`telegram_auth_setting.client_secret`), AES-256-GCM | обмен перехваченного кода авторизации, то есть вход под тем оператором, чей код перехвачен. Доступа к Bot API не даёт и отзывается в BotFather отдельно от токена бота |
| `SERVICE_TOKEN` | env core и бота | доступ ко всем `/internal/*` |
| `AGENT_TOKEN` (переходный, общий) | env core + конфиг ноды, которая ещё не энроллена | чтение desired-state и подделка отчётов/статистики **любой неэнролленной** ноды |
| per-node agent-токен | БД только хешем + `state_dir/identity.json` на ноде (0600) | то же, но **только для своей ноды** |
| bootstrap-токен ноды | БД только хешем; в открытом виде живёт от выпуска до энроллмента, но не дольше `NODE_BOOTSTRAP_TTL_HOURS` | одноразовый обмен на agent-токен своей ноды |
| `DESIRED_STATE_SIGNING_KEY` | env/vault core | подпись поддельного desired-state, принимаемого агентами |
| `BOT_TOKEN`, `ADMIN_BOT_TOKEN` | env бота | контроль над ботом |
| `BOT_WEBHOOK_SECRET` | env бота | подделка апдейтов |
| Креды мерчантов | БД, AES-256-GCM | доступ к платёжным аккаунтам |
| Reality private key | **только на ноде**, файл `reality_private_key_path` | компрометация ноды; в БД его нет никогда |

## Аутентификация оператора

Способов войти в `/api/admin/*` два, оба кладут в заголовок `x-admin-token` токен сессии: email с паролем и Telegram. Плюс переходный общий `ADMIN_TOKEN` из env. Порядок в `AdminGuard` именно такой: сначала попытка резолвить сессию, общий токен сверяется только если сессия не сошлась.

`ADMIN_TOKEN` считается `superadmin`'ом — иначе первого настоящего superadmin'а неоткуда взять: учётки заводятся только изнутри админки. После того как именная учётка superadmin'а заведена и в неё зашли, переменную из `.env` следует убрать: форма входа по email и паролю в админке есть, `curl` для получения токена больше не нужен.

### Роли

Роль хранится в `user.role` (домен закрыт `CHECK`-ограничением в БД, как и `user.status`) и проверяется на каждом админском запросе — в том же `AdminGuard`, сразу после резолва сессии. Вложенность линейная, три значения:

| Роль | Что открыто |
|---|---|
| `support` | диалоги поддержки (список, ответ, статус, назначение), подсказки ИИ, база знаний на чтение, список подписок и их устройства/расход на чтение, свой профиль |
| `admin` | всё, кроме `/api/admin/merchants/*` |
| `superadmin` | всё, включая ключи платёжных провайдеров |

Требование маршрута объявляется декоратором `@MinRole` на контроллере или отдельном хендлере; **без декоратора действует `admin`** — это и есть fail-closed на новых ручках: забытый декоратор закрывает раздел от саппорта, а не открывает. Тем же механизмом (метаданные маршрута, а не список путей в гварде) помечены три ручки без сессии — `@PublicRoute`: вход по паролю, вход по Telegram и конфиг кнопки Telegram. Роль ниже требуемой — 403, даже если сессия валидна. Проверка ролей в админке (скрытые пункты меню и кнопки) — только удобство; барьер один и он на сервере.

Правила выдачи ролей (`AuthService`):

- роль выше собственной не назначается и учётка с ролью выше собственной не правится — иначе `admin` заводит себе `superadmin`'а и обходит запрет на мерчантов;
- свою учётку нельзя ни разжаловать, ни отключить;
- последнего активного `superadmin`'а нельзя ни разжаловать, ни отключить: без него правка мерчантов закрыта навсегда;
- единственный способ входа не отбирается: Telegram не отвязать у учётки без пароля.

Смена роли отзывает сессии этой учётки: роль читается из БД на каждом запросе, но понижение должно быть заметно оператору сразу, а не «когда обновит вкладку».

### Вход по паролю и сессия

`POST /api/admin/auth/login` ограничен двумя правилами лимитера (по IP и по email, см. «Rate-limit»).

Тела ответа при неизвестном email и при неверном пароле совпадают (`401`, «неверный email или пароль»), но **перечисление операторов этим не закрыто**: `scrypt` считается только если пользователь нашёлся (`operator?.passwordHash ? await verify : false`), поэтому несуществующий email отвечает на порядок быстрее. Разрыв — это ровно стоимость одного `scrypt` (на dev-машине ~31 мс при дефолтных параметрах Node); замер на живом core дал 34–37 мс против 2.8–4.2 мс. Определяется одним запросом, лимитер логина от этого не спасает. Закрывается это сверкой с фиктивным хешем на несуществующем пользователе, чтобы `scrypt` крутился в обеих ветках; сейчас этого нет, см. п. 8 «Незакрытых пунктов».

Пароли — `scrypt` со случайной солью на пользователя (формат `scrypt$<salt>$<hash>`, сверка `timingSafeEqual`): memory-hard, поэтому перебор утёкшего дампа дороже, чем при sha256/pbkdf2, и внешних зависимостей вроде argon2 не нужно.

Токен сессии — 32 случайных байта, **в БД лежит только его `sha256`** (`operator_session.token_hash`); само значение отдаётся один раз при логине и больше нигде не хранится, поэтому дамп БД сессий не открывает. Срок жизни — 7 суток. `resolveSession` на каждом запросе требует одновременно: совпадение хеша, `revoked_at IS NULL`, непросроченный `expires_at` и `status = 'active'` у самого оператора. `last_seen_at` обновляется не чаще раза в минуту — иначе запись в БД на каждый клик.

### Вход по Telegram

Telegram Web Login поверх OpenID Connect: authorization code + PKCE. Ключ проверки входа — отдельная пара `client_id`/`client_secret` из BotFather (Bot Settings → Web Login), а **не токен бота**. Это и было причиной переезда с Login Widget: прежний ключ совпадал с токеном Bot API, поэтому утечка настроек админки означала ещё и возможность писать всей клиентской базе от имени бренда. Секрет лежит в БД зашифрованным `SECRETS_MASTER_KEY`, наружу отдаётся только признак «задан».

Флоу и что на каждом шаге защищает:

| Шаг | Что происходит | Зачем |
|---|---|---|
| `POST /telegram/start` | генерируется `state`, PKCE-верификатор и связующее значение; первые два ложатся в Redis на 10 минут, третье — в httpOnly-куку `cl_tg_oidc` | верификатор не покидает сервер: перехваченный код без него бесполезен |
| экран Telegram | пользователь подтверждает вход | — |
| `GET /telegram/callback` | `state` снимается из хранилища **один раз**, сверяется `sha256` куки, код меняется на токены, подпись `id_token` проверяется по JWKS Telegram (`iss`, `aud`, срок, допуск часов 30 с) | кука привязывает вход к браузеру: без неё чужой код, подсунутый жертве ссылкой, залогинил бы её под аккаунтом атакующего |
| редирект в админку | результат кладётся в одноразовый билет на 60 секунд, в URL уходит только он | токен сессии в адресной строке остался бы в истории браузера и в логах прокси |
| `POST /telegram/exchange` | билет снимается и меняется на сессию | повтор возвращает «ссылка устарела», а не вторую сессию |

Личность берётся из claim `id` (scope `profile`), а не из `sub`: `sub` — непрозрачный идентификатор пары «бот + пользователь», по нему оператора не связать ни с ботом, ни с подписками. Телефон (`phone`) не запрашивается.

Вход по Telegram включён в настройках — обязательное условие: выключенный тумблер не выдаёт даже ссылку на Telegram.

**Незнакомый `telegram_id` доступа не получает.** Он создаёт строку `user` со `status='pending'` и минимальной ролью, ответ — `{status:"pending"}`, сессии в нём нет. До подтверждения такой учётке не открывается ни один экран: `resolveSession` требует `status='active'`. Подтверждает заявку `admin` и выше, назначая роль. Отклонение — `status='disabled'`: повторный вход отвечает «доступ отключён», а не заводит вторую заявку.

Привязка Telegram к уже существующей учётке идёт тем же флоу с намерением `link` (`POST /telegram/link/start` требует сессии, идентификатор оператора кладётся в `state`). Один `telegram_id` — одна учётка, барьер — уникальный индекс `user_org_telegram_uq`, а не проверка в коде.

Чего защита **не** закрывает: тот, кто знает чужой `state`, может «сжечь» начатый вход — `state` снимается до проверки куки, поэтому жертве придётся начать заново. Обратный порядок дал бы перебор куки по одному и тому же `state`, что хуже.

### Отзыв доступа

- `POST /api/admin/auth/logout` — гасит ту сессию, чей токен пришёл в заголовке.
- Смена пароля отзывает **все** сессии пользователя, включая текущую: исключения по своему токену в коде нет.
- Отключение оператора ставит `status = 'disabled'` и отзывает его сессии. Второй барьер — проверка статуса внутри `resolveSession`: даже пропущенная при отзыве сессия отключённого не пройдёт.
- Смена роли отзывает сессии — понижение должно быть видно оператору сразу.
- `purgeExpired` (джоба `maintenance`) удаляет сессии, истёкшие больше 30 суток назад. Это уборка мусора, а не барьер: работать сессия перестаёт в момент истечения.

Чего аутентификация оператора **не** даёт — п. 8 «Незакрытых пунктов»: аудита действий нет, личность оператора доходит до бизнес-логики только в ответе поддержки.

## Аутентификация ноды

Ноды стоят у разных хостеров и в РФ — изъятие или компрометация одной из них считается рабочим сценарием, а не катастрофой. Поэтому у каждой ноды свой секрет: токен ноды A не открывает ноду B.

### Энроллмент

1. Админка: `POST /api/admin/nodes/:id/enrollment` — выпуск одноразового bootstrap-токена (32 случайных байта). В БД уходит только `sha256`; **само значение возвращается ровно один раз**, показать его повторно неоткуда. Повторный вызов инвалидирует прежний токен, но **не** отзывает действующий agent-токен: выпуск «на всякий случай» не должен ронять живую ноду. Токен годен `NODE_BOOTSTRAP_TTL_HOURS` (дефолт 24 ч, `node_identity.bootstrap_expires_at`) — распечатка из админки, забытая в переписке, не остаётся рабочим обменом на agent-токен через полгода.
2. Нода: `POST /internal/agent/enroll` с `{nodeId, bootstrapToken, realityPublicKey, shortIds}`. Единственная ручка агента без `x-agent-token` — её защищает сам bootstrap-токен.
3. Core проверяет хеш и **сжигает токен условным UPDATE** (`WHERE bootstrap_consumed_at IS NULL AND (bootstrap_expires_at IS NULL OR bootstrap_expires_at > now())`), в той же операции выдавая per-node токен и инкрементя `agent_epoch`. И одноразовость, и срок держатся на БД, а не на проверке перед записью: две параллельные попытки с одним токеном иначе обе прошли бы и получили разные токены, а между проверкой срока и записью токен успевал бы протухнуть. `NULL` в `bootstrap_expires_at` означает «без срока» (токены, выпущенные до появления колонки), а не «истёк». Причина отказа уточняется отдельным SELECT уже **после** отказа — иначе «истёк» и «уже использован» выглядели бы одинаково, а лечатся они по-разному.
4. Ответ `{agentToken, agentEpoch}` агент кладёт в `state_dir/identity.json` (0600) **до** начала работы: bootstrap одноразовый, и потерянный при рестарте токен уже нечем перевыпустить со стороны ноды.

Reality: агент присылает **только публичную** половину ключа и shortIds — приватник не покидает ноду никогда. Core одной транзакцией записывает их в **два** места и пересобирает desired-state:

- `inbound.reality_public_key` / `inbound.short_ids` того config-профиля, к которому привязана нода, — это конфиг самой ноды и каскадное плечо relay→exit;
- `host.pbk` / `host.sid` тех host'ов, у которых `node_id` = энроллящаяся нода, — это **клиентский** конфиг подписки: генератор читает `pbk`/`sid` именно из `host` (`subscription.repository.hostRef`). Без этой записи нода с `reality_keypair_mode=generate` поднимала бы Reality с новым приватником, панель показывала бы её зелёной, а хендшейк падал бы у всех её клиентов и у каскада через неё.

Почему не наоборот (не читать клиентский конфиг из `inbound`): приватник живёт на ноде, а `config_profile` может быть общим у нескольких нод, и у каждой из них свой сгенерированный ключ — в одну строку `inbound` они не помещаются. Только у `host` есть `node_id`, то есть привязка ключа к ноде, которая его реально обслуживает. По той же причине обновление host'ов ограничено `node_id`: энроллмент одной ноды не имеет права переписать `pbk` у чужих host'ов того же профиля. `host.sid` меняется, только если текущий уже не входит в присланный набор shortIds, — вручную выбранный shortId энроллмент не трогает.

Пересборка идёт после выдачи токена и её падение не роняет энроллмент: bootstrap уже сожжён, и 500 в этом месте оставил бы ноду без доступа насовсем.

`agent_epoch` namespace'ит `report_id` статистики (`"<epoch>:<seq>"`). Он растёт на каждом энроллменте, поэтому переналитая нода не сталкивается id с уже принятыми батчами прошлой инкарнации — раньше это выставлялось руками, и забытая смена молча теряла статистику.

### Проверка токена

`NodeIdentityService.assertAgent` сверяет `sha256` присланного токена с `node_identity` **той ноды, что стоит в пути запроса** (`safeCompare`, constant-time). У ноды с выданным per-node токеном общий `AGENT_TOKEN` **не принимается** — иначе энроллмент ничего бы не давал. Общий токен остаётся fallback'ом только для нод, которые энроллмент ещё не проходили; при его наличии core пишет предупреждение на старте.

### Подпись desired-state

Задан `DESIRED_STATE_SIGNING_KEY` (приватный RSA в PEM) — core отдаёт конверт `{payload, signature}`, где signature = base64 RS256 по **байтам** сериализованного payload (никакой канонизации JSON между сторонами). Ключ не задан — уходит голый JSON: переходный режим для уже развёрнутых агентов. Битый ключ роняет старт core намеренно, потому что молчаливый откат на неподписанную выдачу — это ровно тот даунгрейд, от которого механизм защищает.

На стороне агента (`cp_public_key_path`) правило анти-даунгрейда: конверт → подпись проверяется всегда; голый JSON → принимается, только если ключ не задан; ключ задан, подписи нет → ошибка; конверт есть, ключа нет → ошибка.

Генерация пары:

```
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out cp-signing.key
openssl rsa -in cp-signing.key -pubout -out cp-signing.pub
```

Приватник — в vault и в `DESIRED_STATE_SIGNING_KEY` (переносы как `\n`), публичный — на ноды в `cp_public_key_path`.

### Шифрование кредов

AES-256-GCM, ключ = `sha256(SECRETS_MASTER_KEY)`, формат `v1.<iv>.<tag>.<ciphertext>`. Подробности и модель угроз — в `payments.md`. Коротко: это защита от дампа БД и бэкапа, **не** от компрометации хоста (ключ и шифртекст на одном боксе).

Core падает при старте, если `SECRETS_MASTER_KEY` пуст или короче 16 символов.

### Маскирование

`@corelink/core-kit/mask` применяется к аудиту исходящих HTTP (`external_api_log`) и к сырым ответам провайдеров, которые сохраняются в `payment.meta`:

- заголовки из списка (`authorization`, `x-service-token`, `x-signature`, `crypto-pay-api-token`, `x-telegram-bot-api-secret-token`, …) → `abcd***yz`;
- поля тела по регулярке `token|secret|key|password|signature|credential|api_key` → так же;
- токен Telegram в URL (`/bot<TOKEN>/method`) вырезается отдельно — иначе он утекал бы через сам адрес.

Аудит-приёмник подключается в `main.ts` и пишет в `external_api_log`; падение записи проглатывается — аудит не должен ронять бизнес-вызов.

### Защита от увода токена через настройки

`settings.api_url` мерчанта принимается, только если это https без user/password и хост в allowlist провайдера. Иначе адаптер пошёл бы по подменённому адресу с расшифрованным боевым токеном (`payments.md`).

## Rate-limit

Скользящее окно (`RateLimitService`): Redis при заданном `REDIS_URL`, иначе память процесса. Ошибка лимитера **пропускает** запрос — доступность важнее барьера. Любое правило выключается нулём в env, без выкатки кода.

| Раздел | Ключ | Дефолт | Зачем |
|---|---|---|---|
| `/auto/*`, `/api/sub/*` | `short_uuid`, IP | 30 и 300 / 10 мин | расшаренная ссылка, перебор `short_uuid` (`subscription.md`) |
| `POST /api/admin/auth/login` | IP **и** email | 10 и 5 / 15 мин | перебор пароля оператора |
| `POST /api/admin/auth/telegram/login` | IP | 10 / 15 мин | перебор подписи виджета; ключа по учётке нет — `telegram_id` в теле ещё не подтверждён |
| остальной `/api/admin/*` | IP | 300 / 60 с | перебор `ADMIN_TOKEN` |
| `/webhooks/*` | IP | 600 / 60 с | заливка мусором до проверки подписи |
| `/internal/*` | IP | 1200 / 60 с | перебор `SERVICE_TOKEN` |

Решения, которые нельзя потерять при рефакторинге:

- **Гвард стоит до гвардов аутентификации.** После них перебор токена отсекался бы 401 и до счётчика не доходил.
- **Ключ — IP, а не токен.** Считать по токену значит заводить счётчик на каждое значение, которое перебирающий сам и придумывает.
- **На логине два ключа.** Только по IP — обходится ботнетом; только по email — обходится перебором учёток. По email нужен второй, более жёсткий лимит, потому что цель у перебора одна.
- **Проверка и отметка атомарны.** В Redis — Lua-скрипт (`EVAL`/`EVALSHA`, `defineCommand`), в памяти процесса — синхронный участок без единого `await`. Раздельные чтение и запись давали окно, в котором N параллельных запросов читали `count=0` до первой отметки и проходили ВСЕ; на логине окно растянуто ещё и scrypt'ом (~50–100 мс), так что «5 попыток за 900 с» превращалось в «сколько влезет в конкурентность».
- **Отметка ставится только за разрешённый запрос.** Иначе клиент, долбящийся в 429, продлевает себе блокировку и не выбирается из неё.
- **Ответ 429 несёт `retry-after`** — в секундах до освобождения самого старого слота окна.
- **Адрес клиента — правый хоп `x-forwarded-for`** (при `SUB_RATE_LIMIT_TRUST_PROXY=true`). Правый, потому что прокси заголовок не заменяет, а дописывает: ближайший к нам хоп — единственный, который поставили мы сами, всё левее прислал клиент. С левым хопом клиент подставлял произвольный заголовок и получал новый ключ на каждый запрос, то есть отключал все лимиты разом. Отсюда инвариант деплоя: перед core стоит **ровно один** доверенный прокси; второй сдвинет нужный хоп и склеит всех клиентов в один счётчик. Топология прокси одна на процесс, поэтому переменная общая с выдачей подписки: вторая переменная про то же самое означала бы возможность настроить их противоречиво.
- **Лимит тела запроса разный по разделам** (`main.ts`): 256 КБ на всё публичное и 8 МБ на `/internal/agent/*`, где приезжает батч статистики с ноды. Один глобальный лимит означал бы либо 413 на статистике (батч навсегда застревал в очереди агента, учёт трафика по ноде вставал), либо 8 МБ на анонимный POST в `/webhooks`.

## Модель угроз выдачи подписки

Тело подписки — plain-text `pbk`, `sid`, адреса и порты всех каналов плюс per-user `vless_uuid`. Кто получил URL, тот получил и карту сети для DPI-блокировки, и рабочую идентичность для кражи трафика. Барьеры сегодня:

| Барьер | Что закрывает |
|---|---|
| UA-гейт `happ` | случайное открытие ссылки браузером/краулером |
| `short_uuid` 12 случайных байт | перебор адресов |
| allowlist статусов (`active`/`trial`) + `expire_at > now()` | доступ после отключения, истечения и у тех, кто ни разу не платил |
| rate-limit по IP и по `short_uuid` | расшаренная в чат ссылка, перебор, бесплатная нагрузка на генератор конфигов |
| HWID device-limit | раздача одной подписки на десяток устройств |
| revoke (`short_uuid` + `vless_uuid`) | штатный ответ на состоявшуюся утечку |

Отдельный барьер — **заглушка не является рабочим профилем**: единственный outbound `blackhole` и catch-all в него. В списке Happ заглушка выглядит обычным профилем, и человек по ней жмёт «Подключить»; с прежним `freedom`-outbound он получал «Connected» и весь трафик напрямую, будучи уверенным, что сидит под VPN. Для аудитории в РФ молчаливый выход из-под туннеля хуже, чем честная ошибка подключения.

Механика и решения, которые нельзя терять при рефакторинге (fail-open лимитера, клиент без `x-hwid`, порядок слотов устройств), — в `subscription.md`.

Чего по-прежнему нет: авто-revoke по `ip_fanout` (`AbuseService` умеет только `suspend`) и любой проверки TLS-отпечатка клиента.

## Незакрытые пункты

Перечислено то, что описано в первоначальном дизайне или заведено в схеме БД, но **не имеет кода** либо закрыто частично. По каждому — что есть, чего нет и чем это грозит.

### 1. Остатки переходного режима аутентификации ноды

Энроллмент, per-node токены и подпись desired-state реализованы (см. «Аутентификация ноды»). Не закрыто:

- **Общий `AGENT_TOKEN` ещё принимается** от нод, которые не проходили энроллмент. Пока переменная задана, изъятая неэнролленная нода вскрывает desired-state всех таких же. Закрывается прогоном парка через энроллмент и удалением переменной.
- **Отзыва agent-токена одной ручкой нет.** Ротация = выпуск нового bootstrap-токена + повторный энроллмент ноды (старый токен перестаёт действовать в момент энроллмента, а не в момент выпуска).
- **`agent_pubkey` и `cert_fingerprint` в `node_identity` не заполняются** — они под mTLS (следующий пункт).

### 2. mTLS между агентом и control-plane

- **Есть:** клиентская половина в агенте — при заданных `client_cert_path` + `client_key_path` он ходит с сертификатом и требует TLS 1.3. Половина конфига (один путь из двух) — ошибка запуска: с одним путём агент молча поднялся бы без сертификата, хотя оператор его настраивал.
- **Нет:** выпуска клиентских сертификатов и их проверки на стороне core.
- **Следствие:** аутентификация агента — только bearer-токен (per-node, но всё же shared secret по природе). Компрометация ноды даёт доступ к её desired-state до перевыпуска токена; клиентский сертификат её не спасёт, но добавил бы второй фактор на транспорте.

### 3. Ключ подписи desired-state опционален

Подпись работает с обеих сторон, но `DESIRED_STATE_SIGNING_KEY` — необязательная переменная: без неё core отдаёт голый JSON. Это сделано осознанно (уже развёрнутые агенты не отваливаются), но означает, что до раскатки ключа на ноды доверие к desired-state держится только на TLS и токене. Процедуры ротации ключа подписи тоже нет: смена требует обхода нод с новым `cp_public_key_path`.

### 4. RLS

RLS нет нигде: ни политик, ни `SET LOCAL`, ни ролей. Изоляция — колонка `org_id` + явный `WHERE` во всех запросах, значение берётся из `DEFAULT_ORG_ID`. Это осознанное решение до первого реального второго тенанта (ADR-3), но при его появлении нужен отдельный проход по всем запросам.

### 5. Rate-limit: лимит без Redis размывается

Разделы закрыты: публичная выдача считается внутри `SubscriptionService` (по IP и по `short_uuid`), остальное — глобальным `RateLimitGuard`. Не закрыто:

- **лимит без Redis размывается**: `REDIS_URL` не задан → окно живёт в памяти процесса, и на втором инстансе `api` общего счётчика нет;
- **ошибка лимитера намеренно пропускает запрос** (доступность подписки важнее лимита), поэтому лежащий Redis = временно снятый rate-limit. Это осознанный размен, а не забытая ветка;
- **отказ на логине тратит окно по IP** до проверки окна по email: запрос, отбитый вторым правилом, слот первого уже занял.

### 6. Анти-абьюз опирается на непроверенный источник данных

`AbuseService.scan` (объём за окно, доля upload, `ip_fanout`) стоит в `SCHEDULE` (`abuse-scan`, раз в два часа) и дёргается вручную через `POST /api/admin/abuse/scan`. Источник данных `traffic_sample` наполняется агентом через gRPC `QueryStats`, но этот путь **не проверен против живого Xray** — пока полагаться на детект по объёму рано, а реакция ограничена `suspend`.

### 7. Идемпотентность создания счёта — сделано, с оговоркой

`IdempotencyService` держит ключи `x-client-request-id` в Redis (`SET NX PX`, TTL 24 ч), поэтому барьер общий для всех инстансов `api`. Захват атомарен: два одновременных запроса с одним ключом не могут оба уйти к провайдеру, второй получает 409. Упавшая фабрика снимает захват, иначе повтор после сбоя провайдера залипал бы в конфликте до конца TTL.

Отличие от `RateLimitService`, которое легко потерять при рефакторинге: там `enableOfflineQueue: false` и ошибка Redis **пропускает** запрос (доступность выдачи важнее лимита), здесь `true` и ошибка Redis **роняет барьер в память процесса**. Пропустить нельзя: это второй счёт у провайдера, а unique-индексы БД ловят двойное зачисление, а не двойной счёт. Цена — ожидание до `commandTimeout` (1 с) на создании счёта, если Redis лежит.

Что остаётся: без `REDIS_URL` (degraded-режим) барьер живёт в памяти процесса и на втором инстансе `api` не работает.

### 8. Учётки операторов — сделано, с оговорками

Учётки, пароли, сессии, роли и вход по Telegram работают (см. «Аутентификация оператора»); форма входа и экраны «Доступ» / «Мой профиль» в админке есть. Не закрыто:

- **Аудита действий нет как класса.** На `user.id` во всей схеме ссылаются четыре колонки: `conversation.assignee_user_id`, `message.sender_user_id`, `operator_session.user_id` и `user.approved_by_user_id`. Кто правил мерчанта, ноду, inbound, тариф или запустил рассылку — не пишется нигде; управление учётками пишет только в лог процесса (`AuthService`, уровень warn), а не в БД.
- **`assigneeUserId` берётся из тела запроса.** `PATCH /api/admin/support/conversations/:id` кладёт его в БД как есть, без сверки с сессией: диалог назначается на кого угодно. Автор ответа в `POST …/reply` берётся только из сессии, поля в теле для него больше нет.
- **Общий `ADMIN_TOKEN` ещё принимается** и считается `superadmin`'ом. Пока переменная задана, весь поимённый доступ обходится одной строкой из `.env`. Теперь это действительно можно убрать сразу после заведения именной учётки — форма входа есть.
- **Перечисление операторов открыто по таймингу.** Тела ответов на неизвестный email и на неверный пароль совпадают, но `scrypt` считается только для найденного пользователя, и разрыв в ~30 мс определяется одним запросом (см. «Вход по паролю и сессия»). Практический вес небольшой — узнаётся факт существования учётки, не пароль, — но заявленной защиты «форма входа не список операторов» сейчас нет.
- **Токен сессии живёт в `localStorage`** админки: XSS его достанет. Для одного-двух операторов приемлемо, при росте команды стоит перейти на httpOnly-cookie.
- **Заявка из Telegram не уведомляет никого.** Она видна только на экране «Доступ»: пока админ туда не зашёл, человек ждёт молча. Алерт оператору (`AlertService`) на неё не заведён.
- **Payload виджета проигрывается повторно** в пределах пятиминутного окна (см. «Вход по Telegram»).

### 9. Ротация секретов

Смена `SECRETS_MASTER_KEY` делает сохранённые креды мерчантов нечитаемыми — процедуры перешифрования нет. Токен ноды ротируется энроллментом (без обхода: bootstrap выпускается из админки), но перевыпуск ключа подписи desired-state и общего `AGENT_TOKEN` по-прежнему требует обхода нод.
