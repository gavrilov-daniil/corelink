# Миграция с Remnawave — P0-инварианты и cutover

Мигрированные клиенты (Happ) держат сохранённый URL подписки и просто исполняют полученный конфиг. Любое расхождение = **молчаливый отвал** (Happ перестаёт обновляться / не коннектится, юзер не видит ошибки). Ниже — инварианты, нарушение любого из которых блокирует переключение.

## P0-инварианты (нарушение = релиз-блокер)

### 1. Reality-ключи — импорт, не регенерация
- node-agent при обычном bootstrap генерит новый Reality keypair → новый `pbk` → у ВСЕХ клиентов ноды рвётся конфиг.
- Для миграции — **brownfield-bootstrap**: импортировать существующий keypair из Remnawave DB / vault на ноду, агент его НЕ перегенерирует.
- Born-on-node (генерация на ноде) — только для абсолютно новых нод.
- Две модели безопасности не держатся одновременно: пока идёт миграция ноды — импорт; после — можно перейти на born-on-node через keypair-ротацию с наложением.

**Состояние кода.** В агенте реализованы оба режима: `reality_keypair_mode=generate` (генерит, только если ключа ещё нет — при перезапуске переиспользует существующий) и `reality_keypair_mode=import` (читает файл, отсутствие файла = жёсткая ошибка, а не тихая генерация нового `pbk`). Приватник наружу не уходит: control-plane присылает плейсхолдер `__REALITY_PRIVATE_KEY__`, агент подставляет содержимое `reality_private_key_path` побайтово при записи файла.

Автоматики раскладки ключа на ноду нет — это ручной шаг оператора. Энроллмент, наоборот, реализован: оператор выпускает одноразовый bootstrap-токен (`POST /api/admin/nodes/:id/enrollment`), агент меняет его на per-node токен и `agent_epoch` и кладёт в `state_dir/identity.json` — руками в конфиг попадает только `node_id` и сам bootstrap-токен. Подробнее — `security.md`, раздел «Энроллмент».

### 2. URL/host/path подписки — байт-в-байт
- Сохранить `panel.gavy.shop` (или CNAME на новый бокс) + **оба** пути: `/auto/<shortUuid>` (мульти-профиль) и legacy `/api/sub/<id>` (базовый Авто).
- Ответные заголовки — байт-в-байт: `subscription-userinfo: upload=…; download=…; total=…; expire=<unix>`, `profile-update-interval`, `profile-title`, `announce`, `support-url`.
- Не переносить на `sub.<domain>` — это отвал всех клиентов.

**Состояние кода.** Оба маршрута реализованы. Legacy-путь ищет сначала по `short_uuid` и только потом по внутреннему PK: у мигрируемых клиентов в сохранённой ссылке стоит `shortUuid`, а не наш id, и без этой попытки вся легаси-база молча получила бы «подписка не найдена».

Два расхождения в заголовках, которые надо проверить на реальном ответе панели перед cutover:
- `upload` в `subscription-userinfo` всегда `0` — значение захардкожено в `happHeaders` (`subscription.service.ts`). Агент снимает и uplink, и downlink, но в `subscription.used_traffic_bytes` копится их сумма, и она уходит в `download`;
- `support-url` и `announce` не отдаются вовсе, если соответствующие переменные пусты. Если боевая панель отдаёт их всегда, значения надо задать.

### 3. Идентичность — verbatim-импорт
- `short_uuid` + `vless_uuid` (+ `trojan_password`/`ss_password` где есть) + HWID-устройства — импортировать **как есть**.
- Инвариант: **на миграции никогда не регенерим** идентичность. `short_uuid` меняется только при явном revoke, не при импорте.
- HWID импортировать (иначе мигрированный юзер упрётся в device-limit заново) или первые N дней держать device-limit в soft-режиме.

**Состояние кода.** Импортёр есть: `POST /api/admin/import/remnawave` (по умолчанию dry-run, запись — `{"apply":true}`), `apps/core/src/import/`. Один прогон переносит и инфраструктуру (серверы, config-профили, ноды, inbound'ы, host'ы), и подписчиков с подписками, HWID-устройствами и squad'ами. Порядок внутри прогона несущий: сначала инфраструктура, потом squad'ы — иначе связывать состав squad'а не с чем.

Три места, где «успешный» импорт молча оставлял бы клиентов без VPN, закрыты и видны в отчёте:

- **Reality-идентичность.** `pbk` панель не отдаёт вовсе — он выводится из приватника (`reality-pubkey.ts`), сам приватник в БД не попадает (вырезается и из `raw_json`). `sid`/`sni`/порт/`flow`/`fingerprint` переносятся дословно; расхождение в любом из них = клиент, который перестаёт коннектиться без единой ошибки. Если приватника в ответе панели нет, `pbk` не выдумывается, а попадает в `warnings`.
- **Состав squad'а.** Squad без строк `squad_inbound` ничего не открывает: подписка не попадает в desired-state ноды, клиент получает валидный конфиг, а Xray рвёт хендшейк. Связывание идёт **по тегу inbound'а** (тег — имя inbound'а в Xray-конфиге ноды, одинаков в обеих панелях; имя config-профиля для этого не годится — профили заводятся у нас руками). Inbound'ы, которых у нас нет (не поднят ни на одной ноде — например `VLESS_XHTTP_WL_DE`), попадают в `warnings`, squad без единой связи — тоже, отдельной строкой. Счётчики: `squadInbounds: {total, created}`, `subscriptionsWithoutSquad`.
- **Клиент, зашедший в бота до импорта.** У его подписки свой `short_uuid`, по нему импорт её не находил и заводил **вторую** — уникального индекса на `subscriber_id` нет (вторая подписка законна, куплена для близких), и оплата продлевала одну строку, пока Happ ходил по другой. Теперь идентичность панели переносится в уже существующую подписку, если её `short_uuid` не встречается в панели; в отчёте это `users.adopted`. Правильный порядок развёртывания (бот поднимается после импорта) — в `deploy.md`.

Что важно знать про повторный прогон (он штатный: сверил dry-run → применил → применил ещё раз после правки в панели):

- Сопоставление держится на индексах БД (`config_profile_org_name_uq`, `node_config_profile_uq`, `host_inbound_address_port_uq`), а не на «проверил и вставил».
- Обновляется только то, чем владеет панель. `ssh_ref`, `ssh_secret` (и остальной SSH-доступ: `ssh_auth_type`, `ssh_user`, `ssh_port`), `capabilities`, `base_json`, `params`, `reality_privkey_ref`, `tag_prefix` и статус ноды импорт не трогает: их заводит оператор или энроллмент агента уже после первого прогона.
- Общей транзакции на прогон нет: обрыв на середине оставляет часть парка перенесённой, повторный прогон доводит остальное. Одна кривая строка (host с неизвестным `alpn`) уносит только себя.
- Профиль, который уже принадлежит другой ноде, импорт не забирает — нода пропускается с объяснением в `warnings`.

Про device-limit: soft-режим сейчас включён по факту — энфорсмента HWID в выдаче нет вообще (`security.md`). Мигрированный юзер в лимит не упрётся, но и ограничение работать не будет.

**Чего импорт не делает и делать не будет.** `channel`/`profile`/`profile_channel` (VARIANTS-модель подписки) в панели не существуют — их состав живёт в хардкоде subgen'а, и переносить оттуда нечего. Отдельно: у FRONT-инбаундов каскада в панели нет host'а (адрес фронта зашит в subgen), поэтому host с `tag_prefix=front` заводится руками — импорт называет такие inbound'ы в `warnings`. Флаг `isHidden` панели не переносится: там он значит «ссылку собирает subgen» и стоит у 11 host'ов из 13, а у нас скрытый host выпадает из всех подписок — что показывать клиенту, решают `channel`/`profile`.

### 4. Golden-config byte-diff (спайк 1, go/no-go)
- Перед cutover: сгенерить новую базу для реального мигрированного юзера и **семантически byte-diff'нуть** против текущего Remnawave `/api/sub/<id>/json`.
- Сверять: список outbounds/каналов, балансеры, top-level observatory (`subjectSelector` = union всех selector), loopback-цепочка (fallbackTag/lo-out/lo-in/routing, последний tier без fallback), split-routing (порядок правил, `freedom`-именование, отсутствие `geoip:`/`geosite:`), split-DNS `UseIPv4`, `sniffing routeOnly:true`.
- Любой diff — блокер до устранения.

#### Что показал первый прогон спайка (сверка с боевой панелью)

Снято read-only с действующей панели. Наши предположения разошлись с реальностью в пяти местах — все исправлены в коде:

| Что | Предполагалось | В бою | Следствие |
|---|---|---|---|
| Порядок head-правил | block QUIC → block BT → private → РФ | **private → BT → QUIC → РФ** | приватные сети первыми: локалка не зависит от блокировок и РФ-списков |
| Стратегия балансера | `leastPing` у всех | tier1 `leastPing`, **tier2 `random`** | требование `leastPing` от всех **отвергало боевой конфиг**; теперь `leastPing` обязателен только для тира с `fallbackTag` |
| DNS | 2 сервера (РФ DoH + зарубежный) | **3**: РФ DoH + зарубежный + plain `1.1.1.1` | если оба DoH порежут вместе с туннелем, клиент остаётся без резолва |
| Зарубежный DoH | `8.8.8.8` | `dns.google` | — |
| `profile-title` / `announce` | простой текст | **`base64:<...>`** | в HTTP-заголовке не бывает кириллицы; без кодирования заголовок битый |

Устройство боевой подписки (8 профилей): «Авто» — 2 тира (5 direct + 5 каскадов через общий front по `dialerProxy`); страновые — 1 тир; **«Россия» и «Белые списки» — вообще без балансера**, catch-all уходит в один именованный outbound, и у них нет РФ-правил (это и есть сценарий `ru_split=false`).

Профиль без балансера (single-outbound) **уже поддержан**: при единственном канале в tier 1 и отсутствии tier 2 генератор не создаёт ни балансера, ни observatory, а catch-all уходит прямо в outbound канала. Валидатор это принимает: цель catch-all может быть и балансером, и конкретным outbound'ом (но не `freedom`/`block` — это означало бы, что весь трафик идёт мимо туннеля или в никуда). Обратный сценарий РФ-правил закрыт флагом `profile.ru_split` (миграция 0005).

Порядок head-правил в коде приведён к боевому и закреплён проверкой в валидаторе: **приватные CIDR → bittorrent → udp:443 → РФ → catch-all**, правил после catch-all быть не должно. Комментарий-заголовок к этой проверке в `validate.ts` остался от старого порядка и вводит в заблуждение — сама проверка корректна.

### 5. Takeover ноды агентом (спайк 2, go/no-go)

Первый прогон сделан локально против поднятого core. Что подтверждено:

| Проверка | Результат |
|---|---|
| Сборка | `go vet` и `gofmt` чистые; статический бинарник **6.4 МБ** (amd64) и 5.9 МБ (arm64), `CGO_ENABLED=0` — на ноду едет один файл, без рантайма и Docker |
| Протокол | Агент сам открывает соединение (dial-out), забирает desired-state по `x-agent-token`, начинает применение |
| Reality-ключ | Плейсхолдер `__REALITY_PRIVATE_KEY__` заменяется локальным ключом: в записанном конфиге плейсхолдеров 0, приватник в панель не уходит. Ключ создаётся с правами `0600` |
| Валидация ключа | Мусор вместо ключа отвергается с внятной ошибкой (`invalid x25519 key`), а не пишется в конфиг |
| Честность отчёта | При неудачном применении агент **не рапортует** applied и оставляет прошлый конфиг («keeping last applied config») — мёртвая нода не светится зелёной |

На нодах тест-стенда (26.09.2026, de-1 и de1-exit, режим `generate`) подтверждены реальный `systemctl restart xray` с новым конфигом, старт Xray с подставленным ключом и снятие статистики через gRPC. **Не** проверено главное — **сохранение `pbk` при перехвате существующей ноды** (режим `import`); для него нужна боевая нода.

Порядок проверки на живой ноде: поставить бинарник и юнит → положить существующий приватный ключ ноды в `reality_private_key_path` → `reality_keypair_mode: import` → убедиться, что `pbk` в панели не изменился → погасить host этой ноды в Remnawave.

## Cutover — нода за нодой (две панели не делят одну ноду)

Два control-plane на одной ноде невозможны — будут драться за список юзеров в одном Xray-inbound.

```
1. Новый бокс поднят, БД зеркалит Remnawave read-only: ОДИН прогон импортёра —
   dry-run (`{}`), сверка счётчиков и warnings, затем `{"apply":true,"withDevices":true}`.
   Переносятся серверы, config-профили, ноды, inbound'ы, host'ы, squad'ы с составом,
   подписчики, подписки и HWID. Руками после этого: host фронта каскада (tag_prefix=front)
   и каналы/профили подписки — в панели их нет (см. п.3 выше).
2. Golden-config byte-diff зелёный на реальном юзере (спайк 1).
3. Спайк 2 зелёный: node-agent забирает ОДНУ exit-ноду без смены pbk.
4. Для каждой ноды по очереди:
   a. node-agent устанавливается на ноду, импортирует существующий keypair, применяет desired-state.
   b. В Remnawave host этой ноды гасится (isDisabled) — Remnawave перестаёт ей управлять.
   c. Выдача подписки для этой ноды идёт уже с нового core.
   d. Проверка на реальном устройстве: коннект + failover direct→cascade.
5. Когда все ноды забраны — выдача полностью на новом core, Remnawave выключается.
```

Критерий готовности к полному переключению: все ноды под node-agent, golden-diff зелёный для выборки юзеров, failover подтверждён на устройстве, заголовки ответа идентичны.

## Маппинг Remnawave → новые таблицы

| Remnawave | Новая модель |
|---|---|
| user | `subscriber` + `subscription` |
| config profile | `config_profile` — по одному НА КАЖДУЮ ноду профиля: у нас 1 профиль = 1 нода, имя профиля = имя ноды панели |
| inbound | `inbound` (+ Reality-идентичность на inbound); переносятся только активные на ноде и только vless+reality |
| node | `node` + `server` (сервер идентифицируется адресом ноды: две ноды на одном IP = один сервер) |
| host | `host`; сырой ответ панели целиком остаётся в `host.advanced.remnawave` |
| internal squad | `squad` + `squad_inbound` (связывание по тегу inbound'а) |
| HWID device | `subscriber_device` |
| XRAY_JSON template | `client_template` |
| VARIANTS (subgen.py, хардкод) | `profile` + `channel` + `profile_channel` — **импортом не переносятся**, заводятся у нас |

## Секреты миграции

Reality-privatekey существующих нод сейчас у Remnawave (панель их генерила и пушила — это та самая «дыра», которую чиним). Для импорта их берём из Remnawave DB / vault. После переноса на born-on-node приватники уходят с сети навсегда. IP, ключи, uuid — только в `~/personality/90-vault/projects/vpn-network-2.md`, в этот репозиторий не коммитить.
