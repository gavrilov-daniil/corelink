# Roadmap

Все 4 контура строятся **вширь**: базовый рабочий функционал каждого, затем углубление.
Контуры: **A** Инфра-ядро · **B** Пользователи и деньги · **C** Поддержка · **D** CRM/воронка.

Принятые решения (не пересматриваем без причины):
- Ядро сети воспроизводим 1:1 (VARIANTS, loopback-failover, geo-free split) — иначе мигрированные клиенты отвалятся.
- Мерчанты — **в БД и управляются админкой**, не в env. Несколько аккаунтов одного провайдера, test/live, включение без рестарта.
- **Два бота**: клиентский (продажи/самообслуживание/поддержка) и админский (алерты операторам).
- `org_id` — колонка везде, RLS-машинерии нет до первого реального второго тенанта.
- Go — только в node-agent (статический бинарь без Docker). Всё остальное TypeScript.

## Сделано

### Фундамент
- Монорепо pnpm+turbo: `apps/{core,bot,admin,node-agent}`, `packages/{db,xray-config,core-kit,payments}`.
- Схема БД — **64 таблицы**, все контуры + partial unique индексы и триггер атрибуции
  (идемпотентность на уровне БД, а не блокировок). 15 миграций.
- `@corelink/core-kit`: HTTP с ретраями/бэкоффом/джиттером и аудитом в `external_api_log`,
  маскирование секретов, идемпотентность (`tryClaim`, `buildIdempotencyKey`),
  AES-256-GCM для кредов, constant-time сравнение. **12 тестов.**

### Контур A — инфра-ядро
- `@corelink/xray-config`: генератор **клиентских** конфигов (VARIANTS + loopback-failover +
  geo-free split + observatory, профиль без балансера для single-outbound) с инвариант-валидатором,
  и генератор конфигов **нод** по ролям (exit/relay/front) с каскадами. Детерминированный
  `config_hash`. **36 тестов** (24 клиентских + 12 нодовых).
- Выдача подписки: `/auto/:shortUuid` и legacy `/api/sub/:id` (с fallback shortUuid→PK),
  заголовки байт-в-байт, base64 для кириллицы, UA-гейт, 503 вместо заглушки при своей поломке.
- Профили подписки правятся из админки: `profile` + `channel` + `profile_channel`, флаг `ru_split`.
- API для node-agent (dial-out pull): desired-state, heartbeat, идемпотентный приём статистики.
- Каскады: скрещивание relay↔exit, статус — непрерывная функция от reported-state обеих нод
  (канал уходит из подписки, если плечо разъехалось).
- node-agent (Go): reconcile-loop, brownfield-импорт Reality-ключей, durable-буфер статистики,
  атомарная запись конфига, systemd-хардненинг.

### Контур B — деньги
- 5 мерчантов: `stars`, `cryptobot`, `oxapay`, `paritypay`, `pal24`. Алгоритмы подписей
  перенесены буквально из прода и покрыты тестами. **22 теста.**
- Управление мерчантами из админки: подключение, ключи (шифруются AES-256-GCM), test/live,
  приоритет, health-check. Наружу креды не отдаются. Базовые URL провайдеров — константы
  кода с allowlist на переопределение.
- Единый платёжный flow вместо 5 copy-paste сервисов: подпись → поиск → сверка суммы →
  атомарный claim статуса → фулфилмент в одной транзакции. Ledger-first: баланс = SUM, append-only.
- **Проверено вживую**: поддельная подпись → 401; валидная → подписка +30 дней и ledger ±500 ₽;
  8 повторных доставок (3 последовательных + 5 параллельных) не задвоили ни дни, ни деньги.

### Контур C — поддержка
- Тикеты (`support_contact`/`conversation`/`message`), приём из бота, ответ оператора
  с фиксацией доставки, статусы и назначение.
- Три барьера идемпотентности на индексах: контакт, один незакрытый диалог,
  дедуп по `telegram_update_id`.

### Контур D — CRM и рассылки
- События воронки (`bot_event` с дедупом по `update_id`), агрегаты воронки и по дням.
- Атрибуция через deep-link `start=c_<CODE>`, first-touch на условном UPDATE,
  снимок источника в платёж — триггером в БД.
- Кампании, ссылки, статистика по `campaign_event` (конверсия, CPA, профит).
- Сегменты с декларативным предикатом, рассылки с материализацией получателей,
  троттлингом и claim'ом в `message_log`, триггерные касания с дедупом по «якорю» триггера.

### Боты и админка
- Клиентский бот (grammy, webhook/polling, способы оплаты из БД, Stars через `replyWithInvoice`)
  и админский алертовый.
- Админка: 11 экранов (поддержка, подписчики, мерчанты, инфраструктура, ноды и каскады, трафик, продажи, рассылки, тарифы, доступ, профиль).
- Доступ операторов: три роли (`support` / `admin` / `superadmin`) с проверкой в `AdminGuard` по `@MinRole`,
  вход по email+паролю и по Telegram Login Widget, самозапись через Telegram — только заявкой с апрувом,
  привязка Telegram к заведённой учётке.

### Воркеры
- Одна очередь BullMQ `core-jobs`, cron-эмиттер на лидере через `pg_try_advisory_lock`,
  11 джоб с расписанием, degraded-режим без Redis, дедуп алертов через таблицу `job_dedup`.
- Safety-net `node-reconcile-sweep` по `desired_hash != applied_hash` (закрывает разрыв
  commit→enqueue) и `payment-reconcile` против тихой потери оплаты.

### Управление сетью и статистика
- Админский API и экран «Инфраструктура»: `server`/`config_profile`/`node`/`inbound`/`host`/`squad`
  с валидацией на границе (порт, роли, тег, reality требует sni, hex-shortIds). До этого сеть
  заводилась только `seed.ts`, то есть добавить сервер было физически нечем.
- Инвариант «1 профиль = 1 нода» — уникальным индексом на `node.config_profile_id`, а не
  комментарием: энроллмент второй ноды перетирал Reality первой, и каскадное плечо relay→exit
  начинало указывать на чужой ключ.
- Правка чего угодно, влияющего на конфиг ноды, поднимает `desiredConfigVersion` и
  перегенерирует desired-state. Удаление под ссылками отвергается текстом, а не падением по FK.
- Экран «Трафик»: итоги и по дням, разрез по странам/нодам, топ подписок по расходу,
  состав парка устройств и платформ.

### Мониторинг сети (этап 1)
- Синтетическая проба из дата-центра раз в 5 минут: настоящий трафик через каждый канал тем же
  outbound'ом, что получает клиент (джоба `node-probe`, `workers.md`). История за 14 дней,
  лента переходов «упал / восстановился» за 90, страница «Мониторинг» (саппорту — на чтение,
  «Проверить сейчас» — admin, через очередь). Сбой самой пробы виден отдельно от падения нод.
- Найдено при проверке и закрыто: локация до энроллмента ноды (Reality-ключа ещё нет) уходила
  клиентам с пустым `publicKey` — XrayCore в Happ на таком конфиге не стартует целиком. Такой
  канал больше не выдаётся, валидатор reality без ключа не пропускает.

**Почему нет трафика по устройству.** Xray считает по email пользователя, а email = `short_uuid`
подписки: все устройства клиента ходят под одним `vless_uuid`, и байты между ними неразделимы
в принципе. Свой uuid на устройство невозможен — идентичность переносится с панели дословно
(`migration.md`, P0-3). Поэтому байты — по пользователю и ноде, устройства и платформы — составом.

### Безопасность и эксплуатация
- Учётки операторов (scrypt, сессии, отзыв при смене пароля и отключении) вместо общего токена.
- Энроллмент ноды: одноразовый bootstrap-токен → per-node токен. Токен ноды A не открывает B.
- Подпись desired-state RS256 на стороне core + проверка в агенте с защитой от даунгрейда.
- Rate-limit на выдаче, логине, вебхуках и служебных ручках (Lua-скрипт, атомарно), HWID device-limit.
- Идемпотентность создания счёта по `x-client-request-id` — в Redis, переживает второй инстанс `api`.
- Production-деплой: образы, compose, Caddy. **Проверен полным подъёмом стека** со смоуком через
  Caddy, а не стартом одного контейнера; CI-джоба `deploy` гоняет этот же путь на каждый push.
- Импортёр из Remnawave: идентичность (`short_uuid`, `vless_uuid`, hwid) дословно, состав squad'ов
  по тегу inbound'а, присвоение подписки, созданной ботом до импорта. Проверен на 122 боевых юзерах.

### Аудит
Пройдены и закрыты две волны. Первая — 77 подтверждённых дефектов (12 P0: деньги и доступ,
безопасность, инфра-ядро), P1 и P2. Вторая — 5 P0: три в деплое (Caddy падал на пустом
`ACME_EMAIL`, команда миграций была нерабочей, вход агентов не проксировался) и два в импортёре
(пустые squad'ы → конфиг без доступа к нодам; вторая подписка у клиента, зашедшего в бота до
импорта). Спайк golden-diff сверил генератор с боевой панелью — пять расхождений устранены
(`migration.md`). **214 тестов.**

## Осталось

### Требует решения заказчика (кодом не закрывается)

1. **Где хостится core.** Beget 1CPU/1GB не потянет новый стек + работающий Remnawave.
   Нужен отдельный бокс, желательно вне РФ-хостинга («Антифрод 2.0»): там же ключ подписи
   desired-state и креды мерчантов.
2. **Спайк 2 на живой ноде.** Локально подтверждено: сборка статического бинарника, dial-out
   по токену, подстановка Reality-ключа с правами `0600`, отказ на мусорном ключе, честный
   отчёт при неудачном применении. **Не проверено на реальной ноде:** режим `import`, то есть
   главное — сохранение `pbk` при перехвате; `systemctl restart xray`; старт Xray с
   подставленным ключом. Нужен доступ к ноде, которую не жалко перевести первой.
3. **Учёт трафика против живого Xray.** gRPC-клиент `QueryStats` написан на stdlib и покрыт
   тестами против фейкового gRPC-сервера. С живых нод тест-стенда данные приходят (26.09.2026:
   de1-exit и de-1 — счётчики пользователей и inbound'ов, окна по 30 с), но сверки байтов с
   реальностью не было — достоверными агрегаты пока не считаем.

### Мониторинг — следующие этапы

Решения заказчика: проба «глазами абонента» — отдельное устройство дома; алерты — пока только
в админке (лента событий), доставку в Telegram не делаем.

| Этап | Что | Зачем |
|---|---|---|
| 2 | **Домашняя проба.** Linux-устройство в РФ-сети (Raspberry Pi и т.п.), runner на systemd timer; точка `kind=home` со своим токеном, эндпоинты раздачи плана пробы и приёма результатов в тот же учёт | блокировки ТСПУ из дата-центра не видны: de-1 из ДЦ «работает», а из МГТС мёртв (бан РКН) |
| 3 | **Детектор по трафику реальных клиентов.** Сигналы по `traffic_sample`: «нода жива (heartbeat и проба из ДЦ в порядке), а байты клиентов упали почти до нуля против обычного для этого часа» — блокировка для клиентов из РФ; «доля ноды в общем трафике резко упала при прежнем общем» — балансировщики в клиентских конфигах увели людей на другие ноды; «у пользователей копейки байт вместо обычных мегабайт» — застрявшие рукопожатия. Событие — в ту же ленту | видит то, что проба не видит: проблему у настоящих клиентов, а не у одной точки наблюдения |
| 4 | **«Диагностика ноды»** в админке (статус агента и Xray, порты, фаервол, журнал Xray по SSH) + **журнал выдачи подписки** (кто, когда, что получил; хранение 30 дней) | разбор жалобы «нет интернета» без ручного SSH |

Ограничения детектора (этап 3):
- нужна база реальных пользователей: включается только для нод, где за час было от ~10 активных
  подписок. На стенде с одной-двумя тестовыми подписками «трафик пропал» неотличимо от «пользователь
  лёг спать», поэтому детектор там молчит до переезда клиентов;
- считается только пользовательский трафик: inbound `api` — это опросы статистики самим агентом,
  на de-1 это 4937 окон из 4939;
- реакция — 10–15 минут (несколько окон подряд), не мгновенно;
- `online_state` сейчас пустой — сигналов по устройствам и IP нет;
- зависит от пункта 3 «Учёт трафика против живого Xray»: данные идут, сверки байтов не было.

### Осознанно не сделано

| Пункт | Почему |
|---|---|
| mTLS агент↔core | клиентская половина в агенте есть, серверной нет. Аутентификация — per-node токен; mTLS добавляет второй фактор, но требует своей PKI и ротации |
| RLS | ADR-3: колонка `org_id` везде, машинерия — при первом реальном втором тенанте |
| Live-дельта юзеров через `AlterInbound` | `TODO(M2)` в `reconcile.go`. Пока изменение состава юзеров = рестарт Xray на ноде |
| Ротация `SECRETS_MASTER_KEY` | процедуры перешифрования кредов нет; смена ключа делает сохранённые креды нечитаемыми (задокументировано в `.env.example`) |
| Чанкинг статистики под тестом | `r.xray.Stats()` — конкретный тип без интерфейса, мок требует рефакторинга. Покрыты буфер и отправка |

## Топ-риски

| Риск | Закрытие |
|---|---|
| Перегенерация Reality-ключей рвёт клиентов | brownfield-импорт keypair (режим `import` реализован), спайк 2 на живой ноде |
| Смена URL подписки — отвал клиентов | тот же host/path/заголовки (`migration.md`) |
| Дрейф генератора → молчаливо сломанный failover | инвариант-валидатор на каждой выдаче + golden byte-diff |
| Две панели дерутся за ноду | cutover нода-за-нодой, host в Remnawave гасится |
| Утечка payload (plain-text pbk + uuid) | UA-гейт, неугадываемый `short_uuid`, дешёвый revoke, rate-limit по подписке и IP, HWID device-limit |
| core на РФ-хостинге изымут | вынести core вне РФ (решение заказчика) |
| Двойная активация платежа | `UNIQUE(provider, provider_payment_id)` + `UNIQUE(payment_id)` на активации |
| Оплата пришла, ноды не узнали | `node-reconcile-sweep` по `desired_hash != applied_hash` |
| Тихая потеря оплаты (вебхук отвечает 200 и на внутреннюю ошибку) | 503 вместо 200, когда обработка не начиналась (мерчант выключен, креды не читаются); на всё остальное — `payment-reconcile` эскалирует операторам |
| Блокировка мерчант-аккаунта | несколько мерчантов одного провайдера + переключение без рестарта |
| Компрометация одной ноды | per-node токен после энроллмента: токен ноды A не открывает desired-state B. `AGENT_TOKEN` остаётся переходным и убирается, когда парк заэнроллен |
